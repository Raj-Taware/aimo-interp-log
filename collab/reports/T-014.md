# T-014: Olympiad self-labelling pipeline and Kaggle dry run

Code is in `self-perturb/scripts/label_gen/` (see its `README.md`). The problem pool is `self-perturb/results/grok/T-014/problems.jsonl`: 173 problems, 90 AIME and 83 AMC, all with integer answers. `problem_id` is the row index (`aime-<row>` / `amc-<row>`) because the AMC `id` column is not unique (49 distinct ids across 83 rows).

The dry run used Kaggle kernel `rajtaware10/aimo-t014-labelgen-dryrun` on 2× Tesla T4, with torch 2.11.0+cu128, CUDA 12.8, transformers 5.13.0, accelerate 1.13.0 and fp16. It used HF `generate` only (no vLLM), with Skywork-OR1-Math-7B as both the solver and the stand-in stage-2 writer. Problems were aime-0/1/2 and amc-0/1/2, with 2 samples each and a 4096-token cap. The kernel queued from 14:15 to 14:39 IST and ran from 14:39 to 16:07 IST. The harness itself took 5304 s, far below Kaggle's 12-hour limit. No canary was run: rule 3 applies to feature dumps, and this task produces no feature dumps. Outputs are in `self-perturb/results/grok/T-014/dryrun/` (`dryrun_report.json` plus logs).

The kill test works as follows (`dryrun_t014.py`). The harness starts a stage and waits until its first batch is written. Then it sends SIGKILL to the whole process group while the next batch is still generating. For stage 1 only, it also appends a half-written JSON line with no newline, to simulate a kill in the middle of a write. It then re-runs the identical command to completion, and runs it a third time, which must finish without loading a model.

**Same pipeline under vLLM (box CPU, mechanics only).** I ran vLLM 0.31.0+cpu with transformers 5.13.0, torch 2.13.0+cpu and Qwen2.5-0.5B-Instruct through the same harness with `--backend vllm`. All three stages passed the kill, resume and no-op checks (`results/grok/T-014/vllm_cpu_smoke/dryrun_report.json`). The vLLM path has not run on a GPU or with the real models. The CPU test needed `--enforce-eager` and a g++ install on the box.

## vLLM version: **0.31.0** (2026-10-05), with transformers 5.13.0 in the same environment

- **Install compatibility.** vLLM 0.31.0 requires `transformers>=5.10.4,<5.18.0` and `torch==2.13.0`. That range includes the pinned **transformers 5.13.0**, and the two installed together on the box. vLLM 0.17 to 0.20 require transformers below 5 or exclude early 5.x, so 0.29.0 or later is needed to keep 5.13.0.
- **Model support,** checked in `vllm/model_executor/models/registry.py` at tag `v0.31.0`:
  - Skywork (`Qwen2ForCausalLM`) and DeepSeek-R1-0528-Qwen3-8B (`Qwen3ForCausalLM`) are native.
  - gpt-oss-120b (`GptOssForCausalLM`) is native and has been since v0.10.1.
  - Olmo-3-7B-Think (`Olmo3ForCausalLM`) was native in v0.11 to v0.17 (via `olmo2`). In 0.31.0 it runs through the Transformers modeling backend (`_TRANSFORMERS_SUPPORTED_MODELS`).
- **Qwen3.5-4B (flag).** Its architecture is `Qwen3_5ForConditionalGeneration`: a hybrid of 24 Gated-DeltaNet linear-attention layers and 8 full-attention layers, packaged as a vision-language checkpoint. **vLLM first supports it in v0.17.0** (PR #34110, release notes). It is native in 0.31.0, and 0.31.0 also fixes a CuteDSL BF16 GDN prefill divergence on Qwen3.5 (#53864). Pass `--text-only` (sets `limit_mm_per_prompt` to 0) so vLLM skips vision-encoder profiling. The fallback is `--backend hf` for that model only, which was proven in T-009. Not yet tested: fp16 on the GDN kernels, so use `--dtype bfloat16` if fp16 fails.
- **Wheel and driver.** The PyPI wheel is built for CUDA 13.0, which needs an NVIDIA driver of 580 or newer. If the Lightning driver is older, use the `+cu129` wheel from the GitHub release assets. gpt-oss-120b (MXFP4) needs `--dtype auto`.

## Estimated H100 hours (`results/grok/T-014/h100_estimate.json`, `estimate_h100.py`)

These figures come from the dry-run token counts. 24 solver generations averaged 2691 tokens when they stopped on their own, and 12 of 24 hit the 4096 cap. For the 12288-token cap I assumed capped generations end at 4096, 8192 or 12288 tokens, giving an average of 3.4k, 5.4k or 7.5k tokens per generation. The kept fraction is 0.67, taken from the dry run.

The full run is 2,768 stage-1 generations plus about 4,600 stage-3 generations, which comes to 25 / 40 / 55 M solver tokens across the three length assumptions. On top of that, gpt-oss-120b would write about 1,000 variants (around 1.5 M tokens, roughly 0.2 h). I added 1 h for model loads and the roughly 65 GB gpt-oss download.

| scenario | H100 hours |
| --- | ---: |
| short traces, 5k tok/s | 2.6 |
| **mid, 3k tok/s (central)** | **4.9** |
| long traces, 1.5k tok/s | 11.5 |

With a kept fraction of 0.5 the central estimate is 4.3 h; with 0.8 it is 5.4 h. The T-015 gate (the 20 train-main-v2 problems through all stages) adds about 0.6 h at the central rate. T4 throughput cannot predict H100 throughput, so the tok/s values are a bracket: the plan assumed 3–6k tok/s. The central case fits in about one 5-hour slot and the 2-slot budget covers up to about 9 h. The pessimistic case would need a lower cap or fewer samples, which T-015 can decide after timing the gate.

## Notes for Claude

1. **Doubled BOS for Skywork.** `chat_ids` tokenizes the templated prompt with `add_special_tokens=False`. I checked the four tokenizers: Qwen3.5, Olmo-3 and DeepSeek give the same ids either way. **Skywork-OR1-Math-7B gets a doubled `<｜begin▁of▁sentence｜>`** under the default `add_special_tokens=True` that T-009's `gen_smoke_v2.py` used (27 vs 26 ids). The new pipeline uses a single BOS, which matches vLLM's own chat path. I did not check or change the feature or geometry code.
2. **Sampling** follows T-009, read from the raw `generation_config.json`. All four models resolve to 0.6 / 0.95 / no top-k, the same as T-009. Stop tokens come from the generation config and are never overridden. Each sample gets a stable seed derived from its key.
3. **Writer prompt.** The prompt and type definitions are in `stage2_variants.py`. They are my wording, since the organizers' prompts are not public. Variants are rejected if they lack tags, are cut off at the cap, are too short, are unchanged, contain `\boxed`, or contain the answer number when the original did not. Up to 2 attempts per pair. The Skywork variants often dropped `$` math delimiters, which the gpt-oss prompt may need to address. `missing_numbers` is only a diagnostic and gives false positives, for example `\log_610`.
4. **Labels** follow the organizers' rule: max_drop = base_acc minus the lowest perm_acc; robust if max_drop is at most 0.10, spurious if at least 0.25, otherwise null. They are computed over the types that have a valid variant, with `n_types` and `complete` recorded. T-015 should filter on `complete=True`, or decide how to handle pairs with missing types.
5. **Code changed after the kernel push.** After pushing the kernel I added vLLM-only options: `--enforce-eager` and `--text-only` in `common.py`, and `--dtype`, `--extra` and `--chunk-size` pass-through in `dryrun_t014.py`, all for the CPU vLLM test. The HF code path is byte-identical to what ran on Kaggle; I diffed against the kernel's copy.
